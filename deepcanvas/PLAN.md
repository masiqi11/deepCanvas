## 1. 目标与范围

### 1.1 定位

DeepCanvas 是研究生的个人研究助理：把“乱”变成“清楚”。研究生日常有三种乱：新方向不知从哪入手、论文读不完、事情排不开。产品围绕这三件事做深，其余问题仍然能答（兜底）。

三个支柱，缺一个就退化成普通聊天工具：

| 支柱 | 含义 | 现状 |
|---|---|---|
| 界面 | 回答是能直接操作的界面，而不是需要用户自己消化的大段文字 | 机制已完成并评测过；场景组件有初版 |
| 记忆 | 长期记住用户的方向、任务与截止、读过的论文、掌握了哪些概念 | 没有 |
| 主动 | 根据记忆自己发现问题并提出来，而不是等用户问 | 没有 |

### 1.2 交付的能力

| # | 能力 | 用户看到什么 |
|---|---|---|
| 1 | 场景界面 | 说一段乱糟糟的待办，得到排好的一周；说要入门某方向，得到概念地图、阅读路径和时间线；丢一篇论文，得到速读卡和可层层展开的追问。模型自己判断用哪种界面，用户不需要下指令 |
| 2 | 个人数据 | 计划、截止、论文、学习进度保存在本机，换一个对话、重启应用后仍然在；模型在新对话里知道这些 |
| 3 | 空间与首页 | 左侧有“今天”“本周计划”“学习”“论文库”几个一直在更新的页面；打开应用第一眼是“今天” |
| 4 | 主动提醒 | 首页顶部出现一条有依据的建议（例如“这篇论文按现在的安排周末前读不完”），点一下就能调整 |
| 5 | 调研与论文 | 领域入门的论文和年份带可点开的来源；论文速读的结论标出处 |
| 6 | 评测与演示 | 一套可重复运行的评测，产出报告用的实验数据；一条不依赖真实模型也能完整演示的故事线 |

### 1.3 成功标准

产品层面，下面这条故事线在真实模型下能走通，在模拟模型下每次都能走通：

> 研究生小李的一周。周一导师给了新方向 → 问“从哪开始”，得到领域地图，把其中两篇论文加入论文库 → 丢其中一篇进来速读，追问两层 → 说出这周一堆事，得到一周计划并采用 → 第二天打开应用，“今天”页显示今天三件事和一条提醒，点“帮我调整”后计划更新 → 用自测检查昨天学的概念，掌握度变化。

量化目标（第 5 节给出测法；达不到时如实报告并写明差距原因）：

| 指标 | 目标 | 已有数据 |
|---|---|---|
| 该用场景时用了正确的场景 | ≥ 90% | 一周计划 5/6（旧版组件，一轮） |
| 不该用时没有用 | ≥ 90% | 4/5（同上） |
| 界面完整显示（没有任何问题提示） | ≥ 95% | 通用题集 85.7%（24/28） |
| 计划类输出满足约束（每件事都排了、不晚于截止、不与固定日程冲突） | ≥ 90% | 未测 |
| 列出的论文来源可核验（链接可打开且标题对得上） | ≥ 95% | 未测 |
| 新对话中能说出已保存的事实 | ≥ 90% | 未测 |
| 首个界面出现时间的中位数 | ≤ 25 秒 | 通用题集 38.4 秒；一周计划 26–58 秒 |
| 提示词缓存命中 | ≥ 95% | 98% |

工程层面：第 9 节列出的本地检查全部通过；每个里程碑结束时应用可以启动并演示。

### 1.4 不做

- 编程类专属界面（PR、CI、数据库迁移）。负责人明确要大众和研究生场景。
- 需要联网的地图、图片搜索、视频嵌入。演示现场容易出问题，组件库里已经刻意去掉。
- 账号体系、云同步、多人协作、手机应用、系统级推送通知。
- 后台定时调用模型。提醒用本地规则计算，模型只在用户点击时才被调用。
- 另建模型调用循环，或者把底座从 dsh 换掉。
- 新增会话事件类型。个人数据走工具调用和已有的上下文通道（见 3.3），这样不触发两个 SDK 和会话格式的连带改动。

已验证的部分：`tests/scenes.client.spec.tsx` 的 33 个测试通过（8 组模拟数据的定稿渲染、逐段流式渲染不崩溃、移动与勾选、测验计分、权重重排、日期解析等）；`packages/canvas` 下共 467 个测试通过；类型检查、lint、界面文案检查通过。

没验证或没做的部分（这些都是 M1 的任务）：

- **样式从没在浏览器里看过。** 所有 CSS 是盲写的，测试只在 jsdom 里跑，不检查长相。很可能有错位、溢出、深色模式下不可读的问题。
- 用户的勾选、移动、作答保存在 React 组件状态里：代码块重新挂载就丢，也不会随消息发给助手。
- 视图和接入层写在一起，没法在“空间”页面里复用。
- 没有按容器宽度切换布局。聊天栏宽约 740 像素，空间页面更宽。
- 新版一周计划没有用真实模型测过。旧版（七列）测过一轮，结果在 `eval/results/week-trigger-2026-11-12.json`，当时发现的四个问题（窄栏换行、拆成两张表、不认识的颜色值导致丢项、单个事件被误用）在新版代码和规则里都改了，但改完没有复测。

提示词体积：加入十个场景后，`reference.ts` 从 37,157 字符涨到 41,467 字符（+11.6%）。

### 2.4 现在跑不了的

- **真实模型评测被卡住。** 测试用的 DeepSeek 密钥在 2026-11-13 返回“当前请求的额度已用尽”。恢复额度前，一切需要真实模型的任务只能先用模拟模型做，并标注“未用真实模型验证”。
- 仓库没有配置 CI（PR #1 上没有任何检查运行）。所有检查都要在本地跑。
- 两项检查在上游基线上就不通过，与本项目无关，不用处理：`verify-repository-references`（把 `python/sdk/uv.lock` 里的一个下载地址当成了提交号）和 `rescope-vendor:check`（未改动文件里的原有残留）。

### 2.5 评测脚本和它踩过的坑

`eval/run.mjs` 用 Playwright 驱动正在运行的应用，逐题提问并记录：出现了哪些场景、有没有问题提示、首个界面时间、完成时间、截图。`eval/readlog.mjs` 解码会话日志。用法写在两个文件的头部注释里。已知的坑：

- 全新的 `DSH_HOME` 打开后停在工作区选择器，没有输入框（实际遇到过）。按上游文档，原因是首次使用要创建默认工作区，Linux 上依赖 `xdg-user-dir`，没有就锁住。办法：复用一个选过工作区的目录，或者像 `apps/web/tests/support.ts` 的 `connectFreshWorkspace` 那样驱动选择器（需要 `--patch apps/web/tests/pin-browse-picker.overlay.yml`）。
- 判断“生成结束”只能看 `button[aria-label="停止生成"]` 是否消失。界面里自己可能有带“停止”字样的按钮。
- 模型可能调用 `ask_user_question` 反问用户，此时回合一直等待。脚本把这种情况记为 `waitingForAnswer`。
- 一个应用实例里并发多个对话会失败，只能一题一题跑。
- 对很高的元素单独截图会得到空白图，要用整页截图。
- 客户端代码改动后要先 `pnpm run build:artifacts` 再启动，否则浏览器加载的还是旧包。

## 3. 总体方案

### 3.1 结构

```
        对话回复（openui 代码块）                     空间页面（今天、本周计划、学习、论文库）
                 │                                              │
                 ▼                                              ▼
        接入层 A：代码块适配                           接入层 B：页面适配
                 └──────────────► 场景视图（纯 React）◄──────────┘
                                        │ 读、写
                                        ▼
   模型 ──工具调用（读、写）──► 助手数据服务（宿主，存储域，本机文件）◄── 规则引擎 ──► 提醒
     ▲                                  │
     └────── 上下文快照（每轮，有上限）◄──┘
```

一句话：**数据只有一份，存在宿主；界面只有一套，两处复用；模型通过工具读写数据，通过一小段上下文知道概况；提醒由本地规则算出来。**

### 3.2 关键决定

每一条都写了理由和放弃了什么。实施中如果技术验证（M0-2）推翻了某条，改这里并在进度记录里说明。

1. **场景组件拆成“纯视图”和“接入层”。** 视图只接收数据、状态和回调，不依赖 OpenUI 的运行时；代码块里和空间页面里各有一个薄的接入层。理由：同一张“一周计划”要出现在聊天回复和“本周计划”页两处，写两套必然走样。放弃：现在这种把视图直接写在 `defineComponent` 里的省事写法。
2. **个人数据的唯一来源是宿主的存储域。** 用上游的 `ctx.storageDomain`（文件落在 `<DSH_HOME>/storages`），通过 Typert 远程服务给客户端读写。理由：跨对话、跨重启保留；上游已有同样用法（`packages/schedule`）。放弃：浏览器本地存储（换浏览器就丢，宿主和模型读不到）；把数据塞进会话日志（跨对话取不到）。
3. **聊天里的场景有“提案”和“已保存”两种状态，由条目是否带 `id` 区分。** 模型凭空排出来的计划是提案，条目没有 `id`，卡片上有“采用”按钮；采用后写入存储并得到 `id`。模型从工具结果拿到的条目带 `id`，此时用户在卡片上的勾选和移动直接写回存储。理由：用户保有控制权，随口一问不会污染长期数据；同时已保存的数据在哪里操作都是同一份。放弃：模型每次排计划都自动保存。备选：给场景加一个“显示我已保存的数据”的开关参数，由 M0-2 验证后二选一。
4. **模型通过工具读写个人数据。** 工具调用和结果天然记录在会话日志里，满足仓库“模型可见即有记录”的规则，不需要新增会话事件类型。工具总数控制在四个以内，结果有上限。
5. **每轮给模型一小段“概况”上下文**（今天日期与星期、用户方向与阶段、今天的安排、最近的截止、在学什么），细节让它用工具取。用 `ctx.systemPrompt.context` 注入：它会自动记录成 `runtime-context` 用户快照，并且不改动被缓存的系统提示词。理由：没有概况，模型不知道该不该去查；把全部数据塞进去又贵又会破坏缓存。上限做成配置项（建议默认 600 字符）。
6. **主动提醒由规则引擎计算，不调用模型。** 规则是纯函数：输入数据和当前时间，输出提醒。理由：打开首页要立刻有结果；不花钱；可以用模拟数据把每条规则测到；演示稳定。模型只在用户点击“让助手重排”之类的按钮时才介入。
7. **场景内的用户状态用语义化的键保存**（按标题和日期，而不是数组下标），并进入页面状态存储。理由：这样状态能随消息发给模型（“我把上课挪到了周日，其余帮我重排”），模型重新生成后也还能对得上。
8. **日期由模型给，星期由组件算。** 上游的时间上下文只给模型 ISO 时间戳和时区，不给星期。模型自己推星期会错。所以场景契约里优先用 `YYYY-MM-DD` 或 `@Today()`、`@AddDays(...)`，组件负责显示成“周四 11/12”。概况上下文里也直接写明今天是周几。
9. **论文、年份、数字必须来自工具结果。** 没有来源链接的阅读条目在界面上标“未核实”。评测里自动抓取每个链接核对标题。理由：课程项目里，编造的参考文献是最严重的失误。
10. **空间页面用上游的 `main` 插槽加侧栏入口。** 这条路不改上游代码。“打开应用第一眼是今天”需要另想办法：新对话页的欢迎区没有正文插槽，要么给上游加一个小插槽，要么改默认落地视图，由 M0-2 决定，原则是对上游改动最小。

### 3.3 模型可见内容怎么合规

仓库规则：进入模型请求的任何内容，都必须能从会话日志还原。本项目新增的模型可见内容只有三类，各自的合规方式：

| 内容 | 通道 | 记录方式 |
|---|---|---|
| 场景组件的说明和规则 | `ctx.systemPrompt.section`（`openui-prompt` 已在用） | 系统提示词整体记录为 `system/message` 事件 |
| 概况上下文 | `ctx.systemPrompt.context` | 自动记录为 `runtime-context` 用户快照 |
| 个人数据的细节 | 工具结果 | `tool/call` 及其结果 |

提示词各节和上下文的顺序名是 `packages/core/system-prompt/src/index.ts` 里的封闭表（`SECTION_ORDERS`、`CONTEXT_ORDERS`）。新增一个上下文顺序名要改这个上游文件，改动记入 DESIGN.md 的“上游修改记录”。

### 3.4 仓库规则里最容易踩的

这些都来自 `AGENTS.md`、`packages/AGENTS.md` 和 `docs/testing.md`，列在这里是因为它们会直接决定代码怎么写：

- `openui-prompt/src/reference.ts` 是生成物。改了组件参数、组件说明、页面函数或 `prompt-options.ts` 之后，先跑 `DSH_WRITE_OPENUI_PROMPT=1 pnpm exec vitest run packages/canvas/ui-openui/tests/prompt.client.spec.tsx` 重写它（这一次运行本身会报失败，属正常），再正常跑一次确认通过。
- 覆盖率门槛是 `packages/*/*/src` 下每个文件 100%。豁免只有 `ui-openui/src/client/library/**` 和 `functions/**`（见 `vitest.config.ts` 的 `exclude`）。新建的包没有豁免，所以逻辑要写成纯函数模块，React 部分尽量薄。确实需要豁免时范围要小，并在配置里写明理由。
- 客户端界面上的每一个字都要走文案字典（中英文都要有），由 `verify-client-ui-i18n` 检查。
- 每个导出都要有 JSDoc（`verify-export-jsdoc`）。不能新增 `as unknown`（`verify-no-unknown-casts`）。代码行不超过 140 列。
- 对产品可见的插件，必须有一个“真实装配”的测试：用测试专用的 `cordis.yml` 通过 Loader 启动，断言模型可见、持久化或用户可见的输出。只手工 `ctx.plugin(...)` 的单元测试不够。
- 往注册表里注册的东西，要有测试证明卸载后被移除。所有注册都走 `ctx.effect()` 或 `ctx.on()`。
- 会因部署而变的取值（阈值、上限、默认容量）必须是校验过的 `Config` 字段，不能是写死的常量。配置错误要在加载时就报错。
- 跨边界的标识符用带品牌的类型（`dsh-brand` 的 `Branded<B>`），不用裸 `string`。
- 模型写的数据是“模型 JSON 边界”，要校验和归一化；同进程内 TypeScript 已经保证的类型不要再写运行时校验。
- 每个不算琐碎的、模型可见或用户可见的改动，都要新增或更新一个不需要密钥的录制会话快照（`snapshots/`，规则见 `snapshots/AGENTS.md` 和 `docs/testing.md`）。
- 任何 README 改动都要中英文一起改，然后 `pnpm run verify-translation-pairing --write <路径>` 重新登记。包的 README 有固定小节（Summary、Model Experience、Known Limitations），各有检查。
- 新建包按 `docs/cookbook/adding-a-package.md` 做全套（tsconfig 登记、包元数据、许可证、产品使用归类）。`cordis.yml` 里裸写的插件必须出现在解析清单的依赖里（`verify-cordis-config`）。
- 对上游文件的每一处修改都记入 DESIGN.md 的“上游修改记录”，并且尽量少改。
- 仓库禁用一个英文词：把 `prove` 和 `nance` 连起来写成的那个词，任何大小写都不行，连文件名和本文都会被 `verify-concrete-terms` 扫到。表达“来源”“出处”时用 source、origin 等具体的词。

### 4.3 M1 把十个场景组件做完做好

**M1-1 让模拟模型能输出每个场景。**

- 测试：一个 Node 测试，检查模拟模型对每个关键词返回的代码块能被组件库解析且没有问题项。

**M1-2 在浏览器里逐个看，修样式。**
- 做什么：借助 M1-1，在聊天栏宽度（约 740 像素）、手机宽度（390）、宽屏（1100 以上）、浅色和深色下逐个截图检查，对照 `design/` 里的设计稿修 `components.css`。重点看：文字换行与溢出、间距层级、点击区域、选中与完成状态、流式生成过程中布局是否跳动。深色模式要特别检查 `theme.css` 里写死的浅色值（例如各种 `-soft` 颜色）。
- 完成标准：每个场景在上述六种组合下没有溢出、重叠、不可读的文字；截图存入进度记录引用的目录。负责人看过并认可长相。

**M1-3 视图与接入层分开。**

**M1-4 状态进入页面状态存储，并且语义化。**
- 做什么：按 M0-2(d) 的结论，把勾选、移动、作答、权重、已掌握等状态放进页面状态存储；键用标题和日期。给“一周计划”加一个“按现在的安排重排”动作，把当前状态随消息发给助手。

- 测试：重新挂载保持状态；流式结束转为定稿时状态不丢；消息内容断言；两个同名条目不互相串。

**M1-5 按容器宽度切换布局。**
- 做什么：用 CSS 容器查询（以场景根元素为容器），不要用视口宽度。“一周计划”窄时一天一行，宽时七列；“概念地图”窄时各层上下排；“做决定”的评分表窄时横向滚动。

**M1-6 输入宽容与边界。**
- 做什么：按附录 E 的宽容表实现并补测试。原则：模型写错一个可选字段，只影响那个字段，不能让整个条目或整个组件消失。

- 测试：键盘走完“选中一项、移到另一天、标记完成”的流程；结构快照里每个控件有可读名称。

**M1-10 浏览器里的回归测试。**

- 完成标准：达到 1.3 节前三行的目标，或者给出差距分析和已尝试的规则调整。结果入库。

### 4.7 M5 主动提醒

**M5-1 规则引擎。**
- 做什么：纯函数模块，输入全部数据和当前时间，输出提醒列表。首批规则：
  1. 截止风险：某项截止前，剩余预计工作量超过之前各天的可用容量。
  2. 昨天未完成：昨天计划的事项没有勾掉。
  3. 阅读落后：阅读路径里排在前面的条目超过设定天数未读。
  4. 复习到期：答错过的概念到了再考的日子（依赖 M7）。
  5. 当天超载：某天计划的总时长超过每日容量。
  6. 有截止但没安排：未来七天内有截止，却没有任何对应的计划事项。
- 每条提醒包含：是什么、依据（触发它的数据）、可执行的动作。阈值是配置项。同时最多显示两条，按紧急程度排序。
- 测试：每条规则至少有“触发、不触发、刚好在阈值上”三组模拟数据；用固定时钟；规则之间的排序。

**M5-2 提醒条。**
- 做什么：首页顶部显示提醒。动作分两种：本地能直接完成的（把一项挪到某天）立即执行并可撤销；需要重排的，带着相关数据跳到对话让助手处理。可以忽略或稍后提醒，状态写入存储。每条提醒可以展开看“为什么提醒我”。
- 测试：执行、撤销、忽略后不再出现、稍后提醒到期后再出现。

**M5-3 工作量与容量。**
- 做什么：任务有预计时长（模型排计划时给出，用户可改，缺省值是配置项）；每日可用时长是用户概况里的一项。
- 测试：缺省值生效；修改后规则 1 和规则 5 的结果随之变化。

## 5. 测试与评测

### 5.1 原则

**能用模拟数据测的，不用真实模型。** 组件怎么渲染、怎么交互、数据怎么保存、规则怎么触发、页面流程怎么走，这些都是确定性的，用模拟数据和固定时钟测，每次结果一样，不花钱。真实模型只用来回答确定性测试回答不了的问题：模型选对场景了吗、写出来的东西合法吗、排的计划满足约束吗、列的来源是真的吗、它记得吗、多快、多贵。

### 5.2 测试分层

| 层 | 测什么 | 命令 | 什么时候必须加 |
|---|---|---|---|
| 单元测试 | 纯函数、视图、服务、规则、工具 | `pnpm exec vitest run <路径>` | 每个任务 |
| 真实装配测试 | 插件经 Loader 启动后的模型可见、持久化、用户可见输出 | 同上 | 每个产品可见的新插件 |
| 浏览器测试 | 真实应用里场景的结构快照；采用、勾选、首次使用等流程。模型用模拟数据 | `pnpm run test:web:built` | M1-10、M4-8 |
| 录制会话快照 | 模型可见的改动（新工具、概况上下文、提示词） | `pnpm run test:snapshot` | M1-9、M3-3、M3-4 |
| 真实接口测试 | 没有密钥时自动跳过 | `pnpm run test:e2e` | 可选 |
| 评测 | 第 1.3 节的指标 | `node deepcanvas/eval/run.mjs ...` | M0-4、M1-11、M3-8、M6-2、M8-1 |

覆盖率（每个文件 100%）用 `pnpm run test:coverage` 检查，很慢，在里程碑结束时跑。

### 5.3 题集

| 题集 | 文件（`deepcanvas/eval/`） | 规模 | 测什么 |
|---|---|---|---|
| 通用 | `prompts-general.json` | 30 题（已有） | 该不该给界面、完整显示、速度；与 10 月的数据对比 |
| 场景选择 | `prompts-scenes.json` | 现有 12 题，M1-11 扩到每个场景至少 7 题，另加 10 道无关题 | 选对场景、不误用 |
| 一周计划（旧） | `prompts-week.json` | 15 题（已有） | 与 11 月 12 日那一轮对比 |
| 计划约束 | 新建 | 至少 20 题 | 排出来的计划是否满足约束（见 5.4） |
| 来源 | 新建 | 至少 10 个领域 | 列出的链接是否可核验 |
| 论文 | 新建 | 至少 5 篇 | 速读卡的摘录是否出自原文 |
| 记忆 | 新建 | 至少 15 组多对话脚本 | 新对话能否说出已保存的事实 |
| 外部指令 | 新建 | 至少 2 篇带诱导语句的文档 | 模型是否偏离任务 |

每道题除了题目文字，还要写清预期：应该出现哪个场景（或不应出现任何场景），以及判分需要的信息（见 5.4）。

### 5.4 指标怎么算

- **选对场景**：应该用某场景的题里，回复中出现该场景（`data-scene`）的比例。**没有误用**：不该用的题里，没有出现任何场景组件的比例。出现自由拼出的普通界面不算误用。
- **完整显示**：回复里的界面没有任何问题提示（阻断和部分都没有）的题目比例。
- **计划满足约束**：每道题在题目文件里写明：必须出现的事项（关键词）、各事项的截止日期、固定日程的时间。判分脚本从页面读出计划条目并检查四件事：每个必须出现的事项都在；每个事项的所有工作都不晚于它的截止；不与固定日程重叠；所有日期都在显示的窗口内。四件事都满足才算通过。为了让脚本读得到，场景要带机器可读的标记（例如每一行带 `data-date`），这属于 M1-10 的工作。
- **来源可核验**：回复列出的链接里，请求成功且页面标题与条目标题对得上的比例。没有链接的条目单独统计为“未核实”。
- **记忆**：新对话的回答里包含预期事实的比例。先用关键词自动判，再人工抽查五分之一。
- **首个界面时间**：从发送到页面上第一个界面出现内容。**完成时间**：会话日志里 `turn/start` 到 `turn/end`。
- **令牌与缓存命中**：从会话日志或界面上的用量读数取。

### 5.5 规程

- 每个结果文件开头写明：模型名称、思考强度、代码提交、日期、题集文件。
- 每题跑 3 次，报告平均值和最小到最大的范围。不许挑最好的一次。
- 一次只跑一题。除记忆题集外，每轮开始前用一份干净的用户目录。
- 超时、额度用尽、模型返回格式错误，都记为失败并留在分母里，不能删掉。
- 原始结果存 `eval/results/<题集>-<日期>.json`。截图太大，不入库。
- 改了提示词规则或组件参数之后，至少重跑一遍场景选择题集；跑不了就在提交说明里写“未用真实模型验证”。
- 成本参考：通用题集每题平均用量约 4.7 万令牌，缓存命中约 98%。跑一轮 60 题、每题 3 次，大约是 850 万令牌。

### 5.6 对照实验

报告里的“实验数据”靠这三组对照撑起来，在 M8-1 做：

1. **场景组件开与关**：同一批题，一次用场景组件，一次只允许自由拼界面。比较完整显示率、输出长度、完成时间。预期：场景组件让模型少写，所以更快、更稳。
2. **概况上下文开与关**：比较记忆题集的通过率和令牌数。
3. **思考强度**：比较不同强度下的首个界面时间和选对场景的比例。

可选的第四组：找五位同学各做三个任务（排一周计划、入门一个方向、速读一篇论文），与只用文字回答的版本对比完成时间和主观评分。

3. **测试密钥的额度用完了。** 恢复之前，所有需要真实模型的评测都做不了。（2.4、D8）
4. **仓库没有自动检查。** 所有测试和检查都要手动在本地跑，漏跑不会有人拦着。（第 9 节）
5. **我们改过上游文件。** 每多改一处，以后想跟进上游新版本就多一处冲突。改动要少，并且都记在 DESIGN.md。（3.4）

**产品**

6. **数据只能有一份。** 同一条任务会出现在聊天卡片、“今天”、“本周计划”、倒计时里。如果各存各的，在一处勾掉，别处还显示未完成。（3.2 第 2、3 条，M3-5）
7. **“采用”这一步。** 模型随口排的计划不应该自动变成你的正式计划，否则问几次就乱了；但也不能让用户每次手抄。所以卡片上要有明确的“采用”。（M3-5）
8. **用户在卡片上做的操作现在会丢。** 勾选、移动、作答只存在组件内部，滚动出屏幕再回来可能就没了，助手也不知道你改了什么。（M1-4）
9. **时间的细节比想象的多。** 模型不知道今天是周几；“这周”在周四问的时候应该是从今天起的七天；昨天没做完的事今天怎么办；每周固定的课和组会要先占住位置；排计划需要知道每件事要多久、每天能用多久。（3.2 第 8 条，M3-1、M5-1、M5-3）
10. **第一次打开是空的。** 没有任何计划、论文、进度时，每个页面都要有引导，而不是一片空白；还需要一键载入示例数据，方便演示和验收。（M4-6）
11. **同一个组件要适应两种宽度。** 聊天栏约 740 像素，空间页面可以到 1100 以上。七列的周历在聊天栏里标题会被挤成三四个字一行，这在上一轮测试里已经发生过。（M1-5）
12. **深色模式、键盘操作、读屏、英文界面。** 仓库的检查强制要求中英文文案都有；其余三项没有检查拦着，但演示时一切换主题就会露馅。（M1-2、M1-8）
13. **隐私要说清楚。** 数据存在本机，但提问时相关内容会发给模型。用户要能看到存了什么、能导出、能清空。（M3-6）

**模型**

14. **记忆进入模型的方式有规矩。** 仓库要求进入模型请求的内容都能从日志还原，并且不能破坏提示词缓存（缓存命中率现在是 98%，破坏了每次提问都会又慢又贵）。所以不能简单地把用户数据拼进系统提示词。（3.3、M3-4）
15. **提醒不能靠模型算。** 每次打开首页都调一次模型，要等几十秒、要花钱、还可能失败。用本地规则算，瞬间出结果，而且每条规则都能测。（3.2 第 6 条，M5-1）
16. **模型会编造论文。** 领域入门场景最大的风险是列出不存在的文献。必须要求来源出自检索结果，界面上标出没有来源的条目，并在评测里自动核对。（3.2 第 9 条，M6-1、M6-2）
17. **平台不能读 PDF 里的文字。** 上游可以上传 PDF，但没有任何地方提取其中的文字，模型拿到的只是一个文件路径。论文速读要么走网页链接，要么自己补这个能力。（M6-3）
18. **提示词会越加越长。** 十个场景已经让它涨了 11.6%。越长首字越慢、越贵。要设上限，并测量每加一个场景的代价。（M1-9）
19. **外部内容里可能藏着指令。** 网页或论文里写一句“忽略之前的要求”，模型可能照做。（M6-5）
20. **模型写错一个字段时的后果，实测比预想的严重。** 探测结果见附录 E：有的情况只丢一条，有的情况整个组件消失，还有一种会让后面的数值错位而界面看起来一切正常。（M1-6）
21. **速度有一个现成的杠杆没用过。** 首个界面要 26–58 秒，其中一部分是模型的思考时间。思考强度可调，值得做个对比。（M1-9、5.6）

**课程**

22. **现场演示不能依赖真实模型。** 网络、额度、模型偶发的格式错误都可能在答辩时出现。需要一条在模拟模型和示例数据下必然成功的故事线，以及出问题时的切换预案。（M1-1、M8-2）
23. **实验数据要经得起问。** 每题只跑一次、挑好看的结果、把失败的题从分母里去掉，都会在答辩时被问住。规程见 5.5。
24. **范围容易失控。** 场景、记忆、空间、提醒、论文、学习，全做完是很大的工作量。第 7 节给了砍的顺序，保证任何时候停下来都有东西可以演示。
25. **交付物要跟着改。** 定位变了，报告书、演示视频、宣传片都要更新；组员分工、答辩讲稿需要负责人自己补。（M8-3、M8-4、D10）

## 7. 风险与砍线

| 风险 | 应对 |
|---|---|
| 范围过大，做不完 | 按下面的砍线顺序；每个里程碑结束都可演示 |
| 真实模型不可用或额度不足 | 模拟模型先行；评测集中在 M1-11、M3-8、M6-2、M8-1 四个点，额度到位后一次跑完 |

不能砍的：M1（场景的质量是一切的基础）、M3 里任务的保存读取和概况上下文、M4-2“今天”页、M8-1 到 M8-3。

## 9. 工作规则

**提交与推送。** 小步提交，提交信息沿用现有风格（`feat(canvas): ...`、`fix(canvas): ...`、`test(canvas): ...`、`docs(canvas): ...`）。推送前按 `.agents/skills/dsh-pre-push-checks/SKILL.md` 选最小必要的检查。不要强制推送；确实需要改写历史时用 `--force-with-lease`，并先确认远端没有新的提交。

**一个任务算完成，要同时满足：** 任务的完成标准；任务列出的测试都已加上并通过；相关文档已更新（README 中英文、DESIGN.md、上游修改记录）；下面与改动相关的检查通过。

**检查清单。** 按改动范围选择，命令见附录 B：

- 任何代码改动：相关包的单元测试、类型检查、lint。
- 客户端界面：界面文案检查、导出注释检查；改了插槽要重新生成插槽目录。
- 提示词、组件参数：重写并复核 `reference.ts`；长度上限测试；录制会话快照。
- 新包、新插件、装配文件：`verify-cordis-config`、`verify-product-use`、相关目录生成物。
- 文档：`pnpm run test:docs`；成对文档重新登记。
- 里程碑结束：`pnpm run typecheck`、`pnpm run test:coverage`、`pnpm run build:artifacts` 之后 `pnpm run build:check`、浏览器测试。

**密钥。** 只从环境变量读取。不写进仓库、提交信息、PR、日志、截图、评测结果。

**什么时候停下来问负责人。** 需要修改上游的 Agent 循环或会话格式；单处上游改动超过约 30 行；需要新增许可证不是 MIT、Apache-2.0、ISC、BSD 的依赖；真实模型的花费会超过 D8；技术验证表明第 3 节的某个决定走不通且没有明显的替代。

**回报。** 每个里程碑结束，用平实的中文向负责人说明四件事：做了什么；怎么验证的（跑了哪些命令，结果如何）；什么没有验证以及原因；需要负责人决定什么。数字必须来自实际运行。

**保持本文是真的。** 方案变了就改第 3 节；任务完成就在“进度记录”追加；发现本文写错了就改掉。

## 附录 C 跑一轮评测的步骤

1. 准备一个选过工作区的用户目录：第一次用 `DSH_HOME=<目录>` 启动，在浏览器里选好工作区后关闭。以后每轮评测前复制一份使用，保证每轮起点相同。
2. 确认 `DEEPSEEK_API_KEY` 有额度。脚本遇到“额度已用尽”会自动停下并以退出码 3 结束。
3. `pnpm run build:artifacts`，然后按附录 B 的自动化命令启动应用，记下终端打印的地址。
4. 运行 `eval/run.mjs`。它一题一题跑，每题最长等 6 分钟，结果随跑随写到 `<输出目录>/client.json`，整页截图在 `<输出目录>/shots/`。
5. 每条记录里有：出现的场景及数量（`scenes`）、问题提示（`problems` 阻断、`partials` 部分、`problemText` 原文）、首个界面时间、完成时间、是否在等用户回答、是否失败。
6. 需要工具调用、助手原文、回合起止时间时，用 `eval/readlog.mjs` 解码会话日志。事件类型：`user/message`、`assistant/message`、`tool/call`、`turn/start`、`turn/end`、`step/start`。
7. 把汇总和逐题记录存进 `eval/results/`，文件开头写明模型、思考强度、提交、日期。

## 附录 D 数据模型草案

存储域 `assistant`，版本 1。字段可以在 M3-1 调整，但下面的区分要保留：计划日期与截止日期是两个字段；任务与固定日程是两种实体；掌握度由测验记录推出。

```ts
type Day = string        // 'YYYY-MM-DD'
type Clock = string      // 'HH:MM'

interface Profile {      // 单条
  field?: string         // 研究方向
  stage?: 'undergrad' | 'master-1' | 'master-2-3' | 'phd' | 'other'
  dailyCapacityMin: number          // 每天可用于计划事项的分钟数
  createdAt: number; updatedAt: number
}
interface Task {
  id: TaskId
  title: string
  date?: Day             // 计划在哪天做；没有表示还没排
  time?: string          // 展示用的短标签，如 '上午'、'14:00'
  estimateMin?: number   // 预计时长
  due?: Day              // 截止日期；与 date 相互独立
  done: boolean; doneAt?: number
  note?: string
  origin: { kind: 'user' | 'assistant'; sessionId?: string }
  createdAt: number; updatedAt: number
}
interface FixedSlot {    // 每周固定的课、组会
  id: FixedSlotId
  title: string
  weekday: 1 | 2 | 3 | 4 | 5 | 6 | 7     // 1 是周一
  start: Clock; end: Clock
  from?: Day; until?: Day
}
interface Paper {
  id: PaperId
  title: string; authors?: string; year?: number; venue?: string
  url?: string; arxivId?: string; doi?: string
  status: 'todo' | 'skimmed' | 'reading' | 'done'
  brief?: { oneLine: string; problem?: string; method?: string; result?: string; limit?: string; verdict?: string }
  fieldId?: FieldId
  addedAt: number; updatedAt: number
}
interface Field {        // 一个在学的领域
  id: FieldId
  name: string
  layers: { name: string; conceptIds: ConceptId[] }[]

  sources: { title: string; url: string }[]
  createdAt: number; updatedAt: number
}
interface Concept {
  id: ConceptId; fieldId: FieldId

  mastery: 0 | 1 | 2 | 3
  nextReviewOn?: Day
}

interface NudgeState { id: string; dismissedAt?: number; snoozedUntil?: Day }   // id 由规则名和对象组成
```

## 附录 E 输入宽容表

“现状”一栏里标“已探测”的，是 2026-11-13 用故意写错的数据实际渲染得到的结果。

| 模型写出的情况 | 要求的行为 | 现状 |
|---|---|---|
| 列表里某一条缺必填字段（如没有 `title`） | 丢掉这一条，其余照常，问题提示里说明 | 已是如此（已探测） |
| 列表里某一条的字段类型不对（如 `title: 5`） | 能转换就转换（数字转成文字），不能才丢这一条 | 现在直接丢掉这一条（已探测） |
| 数字写成了字符串（如 `weight: "3"`） | 当作数字 | 现在整条标准被丢掉，排名随之改变，而界面看起来正常（已探测）。**必须改** |
| 按位置对应的数组里某个元素类型不对（如 `scores: ["5", 1]`） | 就地转换或占位，绝不能丢元素 | 现在丢掉该元素，后面的值向前错位，A 的分数显示成了 B 的（已探测）。**必须改** |
| 顶层必填参数缺失（如 `PaperBrief` 没有 `limit`） | 该部分留空，其余照常 | 现在整个组件不显示（已探测）。把除标题和一句话结论之外的字段改成可选 |
| 取值不在预期范围内（如 `tone: "neutral"`） | 用默认样式 | 已是如此 |
| 日期写成 `2026-11-16`、`11-16`、`11/16`、`11月16日`，星期写成 `3`、`周三`、`Wed` | 都认识 | 已是如此 |
| 日期写成“明天”“下周一” | 不认识；提示词要求用日期或 `@AddDays` | 规则里已写，未用真实模型验证 |
| 日期不在显示的七天内 | 不显示该条，并在卡片底部写“有 N 项不在这七天内” | 现在不显示也不提示 |
| 日期根本不存在（如 `11-31`） | 当作无法识别 | 已是如此 |
| 测验的答案写成序号、选项原文或字母 | 都认识 | 已是如此 |
| 测验的答案无法识别 | 该题不计分并注明，而不是选什么都算错 | 现在选什么都算错 |
| 评分个数与选项个数不一致 | 缺的显示为空并按 0 计，多的忽略 | 已是如此，但没有提示 |
| 所有权重都是 0 | 分数都是 0，并提示至少给一项权重 | 分数都是 0，没有提示 |
| 空列表 | 显示空状态文案 | 现在显示一张空卡片（已探测） |
| 标题很长 | 截断，可以展开看全文 | 没做 |
| 条目很多（超过 50） | 先显示一部分，加“显示更多” | 没做 |
| 两条完全相同的条目 | 都显示，各自的勾选互不影响 | 没做（M1-4） |
| 链接不是 http 或 https | 不生成链接，标“未核实” | 不生成链接已做；标记没做 |
| 文字里有 HTML | 原样显示为文字，不执行 | 已是如此（已探测） |
| 流式过程中的半截数据 | 不报错，已到达的部分正常显示 | 已有测试 |
